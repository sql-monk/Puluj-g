# Правила іменування та розміщення

## Сторінки

- Використовуйте нижній регістр і `kebab-case`: `message-normalization.md`.
- Розміщуйте сторінку біля її домену в `docs/`; не додавайте новий наративний
  матеріал до `.arch/`.
- Одна сторінка має одну відповідальність: компонент, алгоритм, процес або
  взаємодія. Починайте її з [шаблону](templates/component.md).
- Посилання на локальні файли мають бути відносними та працювати з GitHub.

## Діаграми

- Для кожного компонента, алгоритму, процесу або взаємодії, яку пояснює
  сторінка, створюйте пару `docs/diagrams/<subject>.drawio` і
  `docs/diagrams/<subject>.png`.
- `<subject>` використовує той самий `kebab-case`, що й сторінка.
- PNG експортується з прозорим тлом, є похідним від відповідного `.drawio` і
  не редагується вручну.
- Сторінка посилається на обидва файли: показує PNG через Markdown image та
  дає окреме посилання на редагований `.drawio`.
- Кожну нову пару додавайте до [реєстру діаграм](diagrams/README.md) і
  оновлюйте її командою з [інструкції експорту](diagrams/export.md).

## Коди джерел

- `sources.code` — стабільний ідентифікатор джерела, який видно в admin UI,
  логах, `analytics` і provenance; після створення його не перейменовують.
- Одне джерело — один рядок. Для Telegram джерелом є канал (username), і
  його код завжди `tg_<username у нижньому регістрі>`: `@KPSZSU`,
  `https://t.me/kpszsu` і `kpszsu` дають `tg_kpszsu`. Так admin API
  (`POST /api/admin/sources`), `data/sources.json` і будь-який імпорт
  сходяться на одному коді, і той самий канал не потрапляє в БД двічі — а
  двічі означає, що колектор читає його двічі й кожен пост стає двома
  raw-повідомленнями.
- Правило коду живе в одному місці — `Puluj.Domain.SourceCodes`
  (`Telegram(username)`, `NormalizeTelegramUsername`, `FindTelegramChannel`).
  Не збирайте `tg_…` рядками в інших місцях.
- Коди без префікса, які вже є в БД (`kpszsu`, `kyiv_ova`, …), лишаються
  чинними: БД володіє джерелами, а `SourceSeeder` не перейменовує рядки.
  Захист від дублювання — за каналом, не за кодом: seeder пропускає запис
  файлу, чий канал уже є під іншим кодом, а admin API повертає `409` із
  кодом наявного джерела, і при створенні, і при зміні `channel`.
- Не-Telegram джерела: людський код у `snake_case` для seed-рядків
  (`alerts_in_ua`); admin API генерує `<type>_<hex>` для створених вручну.
- У `data/sources.json` код запису має збігатися з кодом рядка в БД, який
  він описує; інакше seeder заведе нове джерело (для Telegram — лише якщо
  канал ще не зайнятий).
